# QUDO — кудитная дискретная оптимизация распределения ресурсов

Прикладной модуль для «Облачной платформы квантовых вычислений» (ОПКВ):
размещение виртуальных машин по физическим хостам ЦОД с минимизацией
суммарной сетевой задержки при соблюдении ограничений по CPU, RAM и
пропускной способности.

Реализует пункт 2.2.4 технического задания: кудитная формулировка задачи
в виде модели квадратичной безусловной оптимизации, где **каждая ВМ
кодируется одним кудитом размерности, равной числу допустимых хостов**,
и решение этой модели кудитным вариантом алгоритма QAOA.

---

## 1. Математическая модель

Кудитные переменные: `x_i ∈ {0, …, d_i − 1}` — номер хоста для ВМ `i`,
`d_i = |allowed_hosts(i)|`.

```
C(x) = Σ_{i<j} T_ij · L[x_i, x_j]                     сетевая задержка
     + Σ_{h,r} P_{h,r}(x)                             аппаратные ограничения
```

Через индикаторы `y_{i,a} = [x_i = a]` целевая функция становится
квадратичной безусловной (QUDO/QUBO):

```
C(y) = Σ_{i<j} Σ_{a,b} T_ij · L[a,b] · y_{i,a} · y_{j,b} + Σ_{h,r} P_{h,r}(y)
```

Условие «ровно один хост на ВМ» не требует штрафа: кудит по построению
находится ровно в одном уровне. Это и есть основной выигрыш кудитного
подхода перед двоичным кодированием.

Ресурсные ограничения `load_{h,r} ≤ cap_{h,r}` учитываются двумя способами:

| Режим (`--penalty`) | Представление | Переменные | Точность |
|---|---|---|---|
| `slack` | `P·(load + s − cap)²`, `s` — двоичное разложение с ограниченными коэффициентами | +O(log cap) на ограничение | точное |
| `unbalanced` | `λ₁·g + λ₂·g²`, `g = load − cap` | без дополнительных переменных | приближённое |
| `auto` (по умолчанию) | `slack`, если он умещается в лимиты; иначе `unbalanced` | — | — |

Избыточные ограничения (когда суммарные требования всех допущенных ВМ
не превышают ёмкость хоста) из модели исключаются автоматически.

На небольших экземплярах лончер полным перебором проверяет, что минимум
модели совпадает с точным оптимумом задачи, и при расхождении сам
повышает веса штрафов. Итоговая допустимость размещения всегда
проверяется классически — по исходным аппаратным ограничениям.

## 2. Кудитный QAOA и его исполнение на платформе

```
|ψ(γ,β)> = Π_{l=1..p} U_M(β_l) · U_C(γ_l) · |+>
U_C(γ) = exp(−i γ C / s)          фазовый оператор (s — масштаб коэффициентов)
U_M(β) = Π_i exp(−i β (X_{d_i} + X_{d_i}†))   кудитный смеситель (сдвиг уровней)
```

Платформа принимает схемы в формате OpenQASM 2.0, то есть кубитные.
Кудит понижается до кубитов позиционным (one-hot) вложением
`|a⟩_d → |0…1…0⟩` с d кубитами:

* оператор сдвига уровней `X_d + X_d†` в точности совпадает с XY-смесителем
  `exp(−iβ(XX+YY)/2)` на подпространстве однократного возбуждения, поэтому
  схема **не выходит из допустимого подпространства** — некорректных
  результатов измерения на идеальном вычислителе не возникает;
* все слагаемые целевой функции становятся не более чем двухлокальными:
  достаточно `u1` и управляемого фазового сдвига, многоуправляемые
  вентили (MCP) не нужны;
* используются только вентили `qelib1.inc` из перечня графического
  редактора платформы: `x, h, rx, ry, rz, u1, u3, cx, barrier, measure`.

Локальный кудитный эмулятор (numpy) воспроизводит генерируемую схему
**с точностью до машинной погрешности** (проверяется тестом
`tests/run_tests.py`). Поэтому параметры (γ, β) подбираются внутри
контейнера лончера, без расхода квоты на запуски квантовых сервисов,
а на сервис уходит уже готовая схема.

## 3. Соответствие интерфейсам платформы

| Возможность платформы | Как используется модулем |
|---|---|
| Страница «Квантовые вычисления», вкладка QASM | `--qasm-file`: схема QAOA в OpenQASM 2.0 с блоком `// Qubits initional states` — синхронизируется с графическим редактором |
| Сервисы QASM: `ideem_ideal_30`, `ideem_noisy_30`, `qiskit`, `superconducting`, `atom_msu`, `iqc_yb`, `iqc_ca`, `triangulum` | `--backend`; лимит по числу кубитов проверяется до запуска |
| Страница «Квантовая оптимизация», сервисы `simbif`, `icim` | `--qubo-file`: симметричная QUBO-матрица в формате `.npy` + карта переменных в JSON |
| Лончер квантового приложения | параметры в стиле штатных приложений (`--input`, `--output-file`, `--shots`, `--backend`, `--verbose`, `--json`) |
| Лог запуска | строки вида `[YYYY-MM-DD HH:MM:SS.mmm] сообщение`, в конце — `Локальное время расчёта составило … с` |
| Блок «Измерение вероятностей» | последняя строка лога — словарь счётчиков `{"0100": 125, …}` |
| Каталог `/data` | пути по умолчанию; относительные пути раскрываются в `/data` |

## 4. Запуск

```bash
# полный цикл на открытом эмуляторе Qiskit Aer
python qudo_launcher.py --template small --backend qiskit \
    --layers 2 --shots 1024 \
    --output-file /data/qudo-output.json --qasm-file /data/qudo-circuit.qasm

# подготовка артефактов для сервиса платформы
python qudo_launcher.py --input /data/dc.json --mode export \
    --backend ideem_ideal_30 --layers 3 \
    --qasm-file /data/qudo-circuit.qasm --qubo-file /data/qudo-qubo.npy

# разбор результатов запуска схемы на сервисе платформы
python qudo_launcher.py --input /data/dc.json --mode decode \
    --counts-file /data/counts.json --output-file /data/qudo-decoded.json

# точная QUBO-матрица для эмулятора отжига
python qudo_launcher.py --input /data/dc.json --mode export --backend simbif \
    --penalty slack --qubo-file /data/qudo-qubo.npy
```

Основные параметры:

| Параметр | Назначение | По умолчанию |
|---|---|---|
| `--input` / `--template` | входной JSON или встроенный экземпляр (`small`, `constrained`, `medium`) | `small` |
| `--mode` | `solve`, `export`, `decode` | `solve` |
| `--backend` | вычислитель платформы | `local` |
| `--layers` | число слоёв QAOA (p) | 2 |
| `--shots` | число запусков схемы | 1024 |
| `--penalty` | `auto`, `slack`, `unbalanced` | `auto` |
| `--objective` | критерий подбора параметров: `expectation` или `cvar` | `expectation` |
| `--optimizer`, `--restarts` | классический оптимизатор и число стартов | `cobyla`, 3 |
| `--verbose`, `--json` | подробность лога, печать отчёта в JSON | 1, выкл. |

## 5. Формат входных данных

```json
{
  "name": "dc-small-4x4",
  "hosts": [
    {"id": 0, "cpu_capacity": 8, "ram_capacity": 16, "bandwidth_capacity": 10}
  ],
  "virtual_machines": [
    {"id": 0, "cpu_requirement": 2, "ram_requirement": 4,
     "bandwidth_requirement": 2, "allowed_hosts": [0, 1, 2]}
  ],
  "latency_matrix": [[2, 2], [2, 3]],
  "traffic_matrix": [[0, 8], [8, 0]]
}
```

`allowed_hosts` необязателен; если он задан, размерность кудита данной ВМ
равна длине этого списка. Готовые примеры — в каталоге `examples/`.

Выходной JSON содержит описание модели, результат проверки модели,
параметры QAOA, найденное размещение с разбивкой загрузки по хостам,
эталоны (жадный алгоритм, полный перебор), отклонения от оптимума,
статистику измерений и пути к артефактам.

## 6. Что изменилось относительно исходной версии проекта

| Было | Стало | Причина |
|---|---|---|
| Двоичная кодировка кудита (`ceil(log2 H)` кубитов), возможны состояния вне множества хостов | Позиционная (one-hot) кодировка: `d` кубитов, все состояния допустимы | Требование «один кудит размерности, равной числу допустимых хостов»; отсутствие некорректных измерений |
| Многоуправляемые `mcp`-вентили в фазовом операторе | Только `u1` и управляемый фазовый сдвиг через `u1/cx` | `mcp` не входит в `qelib1.inc` и в перечень вентилей редактора ОПКВ |
| Смеситель `rx` + цепочка `cx` (выводит из допустимого подпространства) | XY-смеситель = кудитный оператор сдвига уровней | Сохранение подпространства «ровно один хост на ВМ» |
| Общие параметры γ, β на все слои | Независимые γ_l, β_l, мультистарт, критерий CVaR | Качество решения при p > 1 |
| Slack-переменные обязательны, число кубитов росло | Отсев избыточных ограничений, ограниченные коэффициенты slack, режим `unbalanced` | Размещение схемы в лимиты сервисов платформы (30 кубитов) |
| Жёсткая зависимость от `qiskit` и `qiskit-aer` | Ядро на `numpy`; `qiskit` — опционально (backend `qiskit`) | Запуск в контейнере лончера с минимальными зависимостями |
| Печать результата в stdout произвольным текстом | Лог в формате ОПКВ, счётчики для гистограммы, отчёт JSON, `.qasm`, `.npy` | Интеграция с интерфейсом платформы |
| Проверка модели отсутствовала | Автопроверка «минимум модели = точный оптимум» и автоподбор весов штрафов | Контроль корректности штрафных слагаемых |

## 7. Тесты

```bash
python tests/run_tests.py
```

Проверяется: совпадение минимума модели с точным оптимумом, симметричность
и корректность QUBO-матрицы, обратимость кодирования, эквивалентность
схемы OpenQASM и кудитной эмуляции (через `qiskit.quantum_info`),
принадлежность вентилей базису платформы, сквозной прогон экземпляра
с дефицитом ресурсов.

## 8. Зависимости и ограничения

* обязательно: `numpy`;
* опционально: `scipy` (COBYLA; иначе используется встроенный
  метод Нелдера — Мида), `qiskit` + `qiskit-aer` (backend `qiskit`).

Ограничения:

* локальная эмуляция ограничена размером пространства состояний
  (по умолчанию 2²⁰ уровней); для больших экземпляров используйте
  выгрузку QUBO на сервис отжига или запуск схемы на сервисе платформы;
* в режиме `unbalanced` минимум модели может не совпадать с оптимумом
  задачи — итоговое решение отбирается по точной целевой функции среди
  измеренных состояний;
* глубина схемы растёт как O(p · Σ_{i<j} d_i d_j); для экспериментальных
  процессоров (`superconducting`, `atom_msu`, `iqc_*`) рекомендуется p = 1
  и предварительная транспиляция средствами страницы «Методы компиляции
  и оптимизации» (сервис `qto`).
